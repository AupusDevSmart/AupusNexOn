1Por que existe

Toda unidade consumidora do Grupo A tem um medidor da concessionária (na Aupus, tipicamente um Landis+Gyr E750). Ele é lacrado: não se lê Modbus nele. O que a norma ABNT NBR 14522 obriga é uma Saída Serial de Usuário (SSU): um fio de coletor aberto onde o medidor transmite, uma vez por segundo, um pequeno bloco de bytes com o estado do intervalo de demanda corrente — segundos restantes, posto tarifário, quadrante e dois contadores de pulsos de energia.

Hoje a Aupus lê essa saída com o gateway IMS A-966, que publica em MQTT um JSON por intervalo de 15 minutos. A TON-V2 passa a fazer isso sozinha pela entrada SU+ (borne X14, pino IO48) — um equipamento a menos em campo, e o bucket fechado exatamente no fim do intervalo que a concessionária fatura.

A ideia central em uma frase: a SSU não manda "kW"; manda contadores de pulsos que acumulam desde o início do intervalo de demanda, e diz qual registrador cada contador representa naquele instante. Energia = diferença entre leituras do mesmo registrador × constante Ke (kWh por pulso).

110 baud = 1/110 s ≈ 9,09 ms por bit; um caractere de 10 bits leva ≈ 91 ms. É uma taxa antiga (teletipo), por isso o gerador de baud do ESP32-S3 precisa de pré-divisor — a UART fecha a conta, mas isso se mede na bancada (bit de 9,09 ms no osciloscópio).

Coletor aberto: o medidor só "puxa" a linha para GND; quem leva a 3,3 V é o pull-up R47 (680 Ω) da placa. Repouso = nível alto = idle de UART. Por isso o RX não é invertido. A isolação óptica está do lado do medidor.

Não há delimitador de início/fim nem campo de tamanho: o único sincronismo é o silêncio. Regra: gap > 150 ms ⇒ o próximo byte é o octeto 1 de um bloco novo (150 fica entre 91 ms de um byte e 182 ms do menor silêncio).

Para aprofundar: NBR 14522 §3.4 (tabelas de tempo); qualquer texto básico sobre UART assíncrona (start/stop bits, idle high); datasheet do ESP32-S3, capítulo UART (baud generator com sclk_div, RX timeout).

3Os dois formatos de bloco

O medidor sai de fábrica em um dos dois modos e não muda em operação. O normal serve consumidor puro; o estendido traz o quadrante, indispensável quando há geração (sem ele, energia injetada seria somada ao consumo com checksum válido). Os octetos 1, 2, 4–7 têm a mesma função nos dois; o octeto 3 é incompatível (mesmo byte, significados diferentes) — daí a autodetecção obrigatória.

Armadilha clássica: passar um bloco normal pelo parser estendido "funciona" — lê tarifa verde (bits 4–5 = 01) como quadrante 4 — sem gerar erro nenhum. É por isso que o formato só é aceito após 10 blocos consecutivos coerentes (tamanho + checksum + repetição).

4Validação — LRC e CRC-16 (com exemplo)

Bloco com checksum inválido não entra em cálculo algum. É a única defesa contra dessincronismo, que corrompe todos os campos sem erro de framing.

LRC (bloco normal)

uint8_t lrc(const uint8_t* d, size_t n) {
  uint8_t v = 0;
  for (i = 0; i < n; i++) v ^= d[i];
  return ~v;              // complemento
}

À mão, no frame de referência do manual A-967 01 00 12 16 00 0a 00 f0:
01⊕00 = 01 → ⊕12 = 13 → ⊕16 = 05 → ⊕00 = 05 → ⊕0a = 0F → ⊕00 = 0F; complemento = F0 ✔ (octeto 8).

CRC-16 (bloco estendido)

uint16_t crc16(const uint8_t* d, size_t n) {
  uint16_t crc = 0;
  for (i = 0; i < n; i++) {
    crc ^= d[i];
    for (b = 0; b < 8; b++)
      crc = (crc & 1) ? (crc >> 1) ^ 0xA001
                      : (crc >> 1);
  }
  return crc;   // grava lo, depois hi
}

É o mesmo algoritmo "refletido" do Modbus RTU, mas com init 0x0000 (Modbus usa 0xFFFF). No vetor 3E 80 81 C0 2B 8E 12 o CRC vale 0xB855 → transmitido como 55 B8.

5Decodificação campo a campo (estendido)

segundos       = d[0] | ((d[1] & 0x0F) << 8);        // 12 bits, regressivo
bitReposicao   = d[1] & 0x10;   bitFimReativo = d[1] & 0x20;   // ALTERNAM (detectar mudança)
postoReativo   = (d[1] >> 6) & 0x03;               // 0 nenhum 1 cap 2 ind 3 ambos
postoHorario   = d[2] & 0x03;                       // 1 ponta 2 fora 3 quarto
quadrante      = QUAD[(d[2] >> 4) & 0x03];          // QUAD = {1, 4, 2, 3}
tarifaReativos = d[2] & 0x80;
pulsosAtiva    = d[3] | (d[4] << 8);   pulsosReativa = d[5] | (d[6] << 8);

6Quadrantes e os seis registradores — a parte que vira dinheiro

Medição em quatro quadrantes: o sinal da potência ativa diz o sentido (direta = importando da rede; reversa = exportando/gerando) e o sinal da reativa diz a natureza (indutiva ou capacitiva). O medidor mantém seis registradores de energia, mas cada bloco transmite só dois — os que estão acumulando naquele quadrante.

Erro que vira dinheiro: calcular quadrante como "bits + 1" acerta Q1 e Q2 e erra Q3/Q4 silenciosamente. Como o quadrante define o registrador, reativo capacitivo vira indutivo — e isso é UFER que o cliente paga (ou deixa de pagar).

Posto reativo (octeto 2) diz o que está sendo computado; bit 7 do octeto 3 diz se está sendo tarifado — a regra (indutivo na carga pesada, capacitivo na leve) o próprio medidor resolve. O firmware só lê.

7Regras de acumulação

O contador de cada bloco acumula desde o início do intervalo de demanda. A energia de um trecho é a diferença entre leituras — mas só faz sentido comparar leituras do mesmo registrador. Quatro situações produzem um contador "menor que o anterior", com tratamentos opostos:

SituaçãoO que aconteceuTratamento correto
Troca de quadrante (Q1→Q3)O contador passou a mostrar outro registrador (11 210 → 41)Nem comparar: é baseline do REG2. Delta = 0, sem pico fantasma
Wrap do contadorREG1 passou de 65 535 para 0 e seguiu (65 500 → 40)Energia real: aritmética modular uint16 (40 − 65500) = 76
Reinício do intervaloSegundos saltaram (0 → 899): contadores recomeçam de 0 no intervalo novoBase de todos os registradores vira 0; o 1º bloco novo já conta (delta = valor)
Bloco de fechamento repetido 3×Mesmos segundos e contadores, três vezesIdempotente: só o 1º acumula; os outros são ignorados
// ordem NÃO negociável: rastrear por registrador PRIMEIRO, wrap DENTRO desse rastreio
if (visto[reg]) acumula(reg, (uint16_t)(atual - ultimo[reg]));   // modular: absorve 1 volta
ultimo[reg] = atual; visto[reg] = true;                            // 1º valor só define a base

Bits que alternam (octeto 2, bits 4 e 5): não são flags de nível — invertem a cada evento e persistem. Detectar por mudança contra o último valor; assim, mesmo perdendo um bloco, a transição não se perde. Sanidade útil: com demanda de 15 min e reativo de 1 h, o bit 5 muda a cada 4 viradas do contador de segundos.

8Como a TON-V2 lê

Decisões que o código fechou

  • Pino e UART. O IO48 (SU+) era entrada de contato seco (s1). Com medidor SSU no diagrama, o gerador troca o papel: vira RX da UART0 — que está livre porque o console é USB-CDC (RS485 usa UART1, LoRa usa UART2). O ESP32-S3 roteia qualquer UART para qualquer GPIO: HardwareSerial ssu(0); ssu.begin(110, SERIAL_8N1, 48, -1). O s1 some do /inputs desse firmware.
  • Enquadramento em hardware. setRxTimeout(4) + onReceive(cb, true): a UART entrega o bloco inteiro num callback quando detecta ~36 ms de silêncio — independente do loop principal, que bloqueia em SD/Modbus/LoRa (a spec exige que a recepção nunca dependa disso). O callback só copia o bloco para uma fila FreeRTOS; o parser roda no loop.
  • Bucket = intervalo do medidor. Os deltas vão para acum[REG1..REG6]; quando o contador de segundos reinicia (fim do intervalo), publica-se o bucket do intervalo que fechou e zera-se. O fechamento coincide com o que a concessionária fatura — melhor que o relógio interno do A-966.
  • NVS. Acumuladores e NSU persistem a cada publicação e a cada 60 s: um reboot no meio do intervalo não perde energia.
  • Alarmes. Enlace degradado (30 erros consecutivos → sts=0); bloco normal em instalação cadastrada com geração (não se infere sentido de fluxo — pede-se a saída estendida à concessionária); sanidade do bit 5; taxa de frames inválidos no /diagnostics (ssu_ok/ssu_err/ssu_fmt).
  • LoRa. Numa TON4v2 satélite o bucket (≈120 bytes) sai pelo mesmo caminho dos devices Modbus, e o gateway carimba a hora.

Onde está: lib canônica AupusNexOn/firmware-libs/ssu_nbr14522/ (C++ puro, testável no PC); o gerador embute cópia byte-idêntica e gera ssu.cpp (UART, fila, bucket, JSON) só quando há medidor no diagrama.

9Como o NexON usa

A TON publica o mesmo JSON do A-966, então nada muda no backend para o caminho de dados:

{"NSU":32,"ver":"2.0.0-…","data":{"cdo":"15","phf":0,"phr":1532,"sts":1,
 "qhfi":0,"qhfc":4,"qhri":0,"qhrc":0,"frame":"00 90 a2 fc 05 04 00 c6 18"},
 "time":"1789661700","ke":0.048,"fmt":2,"q":4,"seg":898,"posto":2,"ssu_err":0}
  • Pulsos crus no payload (phf/phr/qh*), 1:1 com REG1…REG6. Quem aplica a constante é o backend.
  • Ke (kWh/pulso) é dado de cadastro por medidor. A TON manda ke no envelope; o NexON usa esse valor (A-966 não manda → padrão histórico 0,048).
  • Contas do bucket de 15 min: kWh = pulsos × Ke; kW médio = kWh ÷ 0,25 h. No exemplo real acima: 1 532 × 0,048 = 73,5 kWh → 294 kW exportados (é exatamente o P_rev que o backend calcula).
  • O equipamento nasce na categoria "Gateway" (mesmo tipo do A-966) — é isso que aciona a ingestão de pulsos, o dashboard do gateway e o fluxo bidirecional na demanda/COA.

Bancada, em ordem

  1. Sem medidor: um 2º ESP32 com simulador_ssu.ino (TX → 1 kΩ → SU+, GND comum) gera blocos a 110 baud; comandos n/e formato, q1..q4 quadrante, w wrap, c bloco corrompido, f fechar intervalo. Primeiro alvo: o formato travar em ~10 s e o bit de 9,09 ms no osciloscópio.
  2. Com E750 e fonte de ângulo: −25° (Q1), +25° (Q4), 155° (Q2), 205° (Q3); ±23,07° dá FP 0,92 — a fronteira regulatória. Confirmar convenção de sinal da fonte contra o mostrador do medidor antes de culpar o firmware. Determinar o Ke real (potência conhecida × tempo ÷ pulsos).
  3. Campo: TON-V2 e A-966 lendo o mesmo medidor por uma semana — buckets idênticos (±1 pulso) antes de desligar o A-966.

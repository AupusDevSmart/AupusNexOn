SSU (ABNT NBR 14522) na TON-V2 — guia de referência

v1.3 · 21/09/2026 · protocolo, firmware, payload, testes e bancada · Aupus Energia · Engenharia IoT · revisão v1.3: nomes dos registradores reativos alinhados ao A-966 real; RX-timeout, wrap de 15 bits e reinício de intervalo aplicados no código; caminho LoRa binário.

Resumo

O que chega1 bloco por segundo: segundos restantes do intervalo, posto, quadrante e 2 contadores de pulsos (ativa, reativa) acumulados desde o início do intervalo.
EnergiaΔ pulsos do mesmo registrador × Ke (kWh/pulso). Nunca comparar contadores de registradores diferentes.
Enlace110 baud, 8N1, coletor aberto, sem delimitador — o bloco é fechado pelo silêncio.
HardwareBorne X14 (X14-2 = SU+, X14-1 = GND) → IO48 · pull-up R47 680 Ω · TVS D4 · UART0 (Serial0), só RX.
SaídaBucket por intervalo de demanda (15 min), JSON no formato do A-966, categoria Gateway no NexON. Em satélite LoRa: JSON plano → frame binário LORA_TYPE_SSU.

Bit = 9,09 ms; caractere ≈ 91 ms. Receber sempre em SERIAL_8N1. RX não invertido (idle alto pelo pull-up). Fechar o bloco em qualquer silêncio entre ~10 ms e 182 ms.

Formatos de bloco

Modo fixo de fábrica. O octeto 3 muda de significado entre os formatos → autodetecção: aceitar o formato só após 10 blocos seguidos com tamanho + checksum válidos. Blocos da detecção não acumulam.

Validação e decodificação

Checksum inválido → descartar o bloco inteiro e contar em ssu_err.

uint8_t lrc(const uint8_t* d, size_t n) {
  uint8_t v = 0;
  for (size_t i = 0; i < n; i++) v ^= d[i];
  return (uint8_t)~v;
}
uint16_t crc16(const uint8_t* d, size_t n) {
  uint16_t c = 0;                 // ≠ Modbus (0xFFFF)
  for (size_t i = 0; i < n; i++) {
    c ^= d[i];
    for (int b = 0; b < 8; b++)
      c = (c & 1) ? (c >> 1) ^ 0xA001 : c >> 1;
  }
  return c;
}
seg      = d[0] | ((d[1] & 0x0F) << 8);
bitRepos = d[1] & 0x10;       // toggle
bitFimR  = d[1] & 0x20;       // toggle
postoR   = (d[1] >> 6) & 3;   // 0 · cap · ind · ambos
postoH   = d[2] & 3;          // 1 ponta · 2 fora · 3 quarto
q        = QUAD[(d[2] >> 4) & 3]; // {1,4,2,3}
tarifR   = d[2] & 0x80;
ativa    = d[3] | (d[4] << 8);
reativa  = d[5] | (d[6] << 8);

Convenção dos nomes (a do A-966, que o NexON consome): f/r = sinal de Q (fornecida = +Q, recebida = −Q); i/c = Q1 e Q3 indutivo, Q2 e Q4 capacitivo — sempre relativo ao sentido do fluxo ativo (o mesmo critério da ANEEL para geração). O backend soma qhfi+qhri como indutivo e qhfc+qhrc como capacitivo.
Base da correção (v1.3): 400 buckets reais do "Gateway IoT A-966 1" (UFV, 17/09/2026) cruzados com o quadrante do frame: ativa Q2/Q3 → phr, Q4 → phf (tabela {1,4,2,3} confirmada); reativa Q2 → qhfc (57×), Q3 → qhri (132×), Q4 → qhrc (158×). O v1.2 trazia Q2→qhri / Q3→qhrc / Q4→qhfc — invertido: uma UFV exportando em Q2 apareceria como indutiva.
Não calcular quadrante como "bits + 1". Acerta só Q1: 01 vira Q2 (consumo contado como injeção), 10 vira Q3 (reativo trocado), 11 vira Q4 (injeção contada como consumo). Sem erro visível — o checksum é válido.

Regras de acumulação

SituaçãoSintomaTratamento
Troca de quadranteContador da ativa cai (11 210 → 41)É outro registrador. Δ contra o último valor do REG2 — 0 se o intervalo foi visto desde o início (reinício observado ⇒ todos os registradores partiram de 0). Baseline só se o REG2 nunca foi visto antes de um reinício (boot no meio do intervalo).
Wrap65 500 → 40 no mesmo registradorΔ modular: 76. Normal (15 bits): mod 32 768 — 32 700 → 40 = 108.
Reinício do intervaloSegundos sobem (0 → 899)Publicar bucket, zerar acumuladores, base de todos = 0 e todos "vistos"; o 1º bloco novo já conta.
Fechamento 3×Blocos idênticos repetidosΔ já dá 0; contar o evento de fechamento uma vez só.
Bits 4 e 5Invertem a cada eventoDetectar mudança contra o último valor. Bit 5 ≈ a cada 4 intervalos (reativo 1 h).
const uint16_t MASK = normal ? 0x7FFF : 0xFFFF;
void processa(uint8_t reg, uint16_t atual) {        // reg = 1..6
  if (visto[reg]) acumula(reg, (atual - ultimo[reg]) & MASK);
  ultimo[reg] = atual; visto[reg] = true;
}
void reinicioIntervalo() {
  publicaBucket(); zeraAcumuladores();
  for (int r = 1; r <= 6; r++) { ultimo[r] = 0; visto[r] = true; }
}

Firmware na TON-V2

static HardwareSerial& ssu = Serial0;   // UART0 = o objeto do core (console é USB-CDC); nunca 2ª instância
ssu.begin(110, SERIAL_8N1, 48, -1);     // RX = IO48, sem TX
ssu.setRxTimeout(1);                    // 1 símbolo ≈ 91 ms — dispara no silêncio de 182 ms
ssu.onReceive(onBloco, true);           // callback só copia para fila FreeRTOS
ItemComportamento
ParserRoda no loop, lendo da fila. A recepção não depende do loop (SD, W5500, LoRa e Modbus bloqueiam por centenas de ms).
Bucketacum[REG1..REG6]; publicado quando os segundos reiniciam — alinhado ao intervalo faturado.
NVSAcumuladores e NSU salvos a cada publicação e a cada 60 s.
Enlace degradado30 blocos inválidos seguidos → sts = 0 e volta à autodetecção.
Alarme de formatoBloco normal em instalação com geração → pedir saída estendida à concessionária.
Diagnóstico/diagnostics: ssu_ok, ssu_err, ssu_fmt, ssu_degradado, ssu_intervalos.
GeradorCom "Medidor Concessionária (SSU)" no diagrama, o IO48 vira RX (sai do /inputs) e é gerado ssu.cpp. Lib: AupusNexOn/firmware-libs/ssu_nbr14522/.
LoRa (TON4v2 satélite)O JSON aninhado do A-966 tem ~236 B e não cabe no MTU de 200 B do E220. No satélite (SSU_LORA_BIN=1) o bucket sai em JSON plano (sem frame/ver/time) e vira o frame binário LORA_TYPE_SSU (0x11, ≈ 90 B no ar); o gateway carimba a hora e republica plano; o backend lê phf/phr/qh* tanto em data.{} quanto no topo. Gateway precisa de firmware com a tabela nova (regravar).

Contas (bucket de 15 min): kWh = pulsos × Ke; kW médio = kWh ÷ 0,25. Ex.: 1 532 × 0,048 = 73,5 kWh → 294 kW exportados.

Exemplo real do A-966 = caso de teste 9. O frame acima decodifica como Q2 (octeto 3 = A2 → bits 5-4 = 10), ativa 1 532 no REG2 e reativa 4 no REG4 → phr = 1532, qhfc = 4 — exatamente o que o A-966 publicou. O ssu.cpp gerado emite o mesmo.

Roteiro

  1. Só tensão: SSU transmitindo, formato travado, segundos decrescendo, contadores parados.
  2. Ke de bancada: Q1, φ = 0, 15 min (ex.: 66,4 V × 5 A × 3 ≈ 996 W → 0,249 kWh). Ke = kWh injetados ÷ pulsos. Repetir com φ = 90° para o reativo.
  3. Um quadrante por intervalo: Q1, Q4, Q2, Q3 — energia só nos 2 registradores do quadrante; conferir que o JSON cai em qhfi / qhrc / qhfc / qhri, nessa ordem.
  4. Transições (Sequencer): Q1→Q4, Q1→Q3, Q4→Q3 no meio do intervalo, várias vezes — sem pico.
  5. FP: φ = 23,0° e 23,2° — FP do NexON = cos φ injetado.
  6. Longa duração: cronometrar o bit 5, observar ssu_err, reboot no meio do intervalo (NVS).
